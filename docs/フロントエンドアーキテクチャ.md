# プロンプトインジェクション検査サイト Web フロントエンド実装方針

## 1. 概要

本プロダクトの Web フロントエンドの実装方針を定めます。**GitHub Pages 上で動作する静的な単一ページアプリ**であり、検知処理はすべてブラウザ内で実行します。保守性と拡張性のため、検知ロジック（backend/domain）と UI（frontend）を明確に分離します。

## 2. 技術スタック

### コア技術
- **Framework**: Next.js 15 (App Router) ／ 静的エクスポート（`output: 'export'`）
- **Language**: TypeScript
- **Styling**: Tailwind CSS
- **State Management**: React 標準（`useState` / `useReducer`）。グローバル状態管理ライブラリは原則不使用
- **Data Fetching**: なし（サーバー無し）。ファイル読込・URL取得はブラウザ API を Gateway 経由で使用
- **Database Client**: なし
- **Form Management**: 軽量なため React 標準で管理（必要に応じて Zod でバリデーション）
- **UI Components**: shadcn/ui

### 開発ツール
- **Linter/Formatter**: Biome
- **Testing**: Vitest（検知ロジックの Unit テスト中心）
- **E2E Testing**: Playwright（任意・クリティカルパスのみ）

## 3. ディレクトリ構成

```text
apps/webapp/src/
├── app/                      # Next.js App Router（静的エクスポート）
│   ├── page.tsx              # 検査ページ（単一ページ）
│   ├── layout.tsx            # ルートレイアウト
│   └── globals.css
├── frontend/                 # UI レイヤー
│   ├── components/
│   │   ├── ui/               # shadcn/ui 基本コンポーネント
│   │   ├── inspection/       # 検査機能の UI（入力・結果・ハイライト）
│   │   └── layouts/          # ヘッダー・フッター等
│   ├── hooks/                # use-inspection.ts 等のカスタムフック
│   └── lib/                  # クライアント側ユーティリティ（cn 等）
└── backend/                  # 検知ロジック（アーキテクチャ.md 参照）
    ├── domain/               # 検知エンジン・ルール定義（純粋ロジック）
    ├── application/          # 検査 UseCase
    ├── infrastructure/       # ファイル読込・URL取得の Gateway 実装
    └── presentation/
        └── composition/      # DI 組み立て（frontend からの唯一の入口）
```

## 4. 機能要件

### Phase 1: MVP

#### 4.1 テキスト検査（コア機能）
- **要件**:
  - テキストエリアへの貼り付け入力と文字数カウンタ
  - 「検査する」実行、またはリアルタイム検査
  - 検知結果（総合リスク・カテゴリ別サマリー・ハイライト・根拠）の表示
  - レスポンシブデザイン（スマホファースト）
- **表示項目**:
  - 総合リスク（安全／注意／危険 or スコア）
  - カテゴリ別検出件数
  - マッチ箇所をハイライトした入力テキスト
  - 検出リスト（マッチ文字列・カテゴリ・説明・重み）
- **機能（初期スコープ）**:
  - 不可視文字の可視ラベル化表示
  - 「サンプルを試す」「クリア」ボタン

#### 4.2 ファイル・URL 入力
- **要件**:
  - `.txt` / `.md` のファイル読込（ブラウザ内処理・アップロードなし）
  - URL入力による内容取得（CORS 制約に応じた対応・要件定義 §10）
  - 入力ソースの切替 UI（タブ／セグメント）

### Phase 2: 機能拡張
- 検知ルールカタログ（手口解説）ページ
- 検出結果のエクスポート（JSON / レポート）
- BYOK による LLM 判定（利用者のキーで高精度化）

## 5. 非機能要件

### パフォーマンス
- First Contentful Paint (FCP): < 1.5 秒
- Time to Interactive (TTI): < 3 秒
- Cumulative Layout Shift (CLS): < 0.1
- 静的生成（SSG）とクライアント検知により初期表示・検査を高速化。大きな入力では検知処理をチャンク／デバウンスして UI をブロックしない

### アクセシビリティ
- WCAG 2.1 Level AA 準拠
- キーボードナビゲーション対応・スクリーンリーダー対応・適切な ARIA 属性
- リスク色分けは色のみに依存せずラベル／アイコンを併記

### プライバシー / SEO
- 入力テキストを外部送信しない（URL取得を除く）ことを明示
- 適切なメタタグ・OGP を設定。単一ページのため sitemap は最小限

## 6. 実装ガイドライン

### コーディング規約
1. **コンポーネント設計**: 単一責任・Props Interface の明確化・適切な分割
2. **型定義**: 全コンポーネントで TypeScript。`any` 禁止。検知結果の型は backend/domain の型を再利用
3. **スタイリング**: Tailwind ユーティリティファースト・`cn()` ヘルパー・レスポンシブ徹底（スタイルガイド.md 参照）

### アーキテクチャ原則
1. **UI と検知ロジックの分離**: 検知は backend/domain の純粋関数。UI は結果を描画するだけ
2. **composition 経由のみ**: frontend は `backend/presentation/composition` からのみ検知機能を利用する
3. **依存関係の管理**: 循環参照を避ける（dependency-cruiser で検証）
4. **テスタビリティ**: 検知ロジックを純粋関数として切り出し、UI から独立してテスト可能に保つ

## 7. 実装順序

1. **基盤構築**: 静的エクスポート設定・Tailwind/shadcn セットアップ・レイアウト実装
2. **検知エンジン実装**: domain のモデル・ルール定義・検知サービス・UseCase（+ Unit テスト）
3. **UI 実装**: 入力（テキスト/ファイル/URL）・結果表示・ハイライト・カスタムフック
4. **統合**: composition で DI 組み立て、page.tsx に統合、動作確認

## 8. テスト戦略

### ユニットテスト（中心）
- 検知エンジン（ルール適用・スコアリング）… 純粋関数として重点的にテスト
- ルール定義（各カテゴリの代表サンプルで検知・非検知を検証）
- ユーティリティ関数・カスタムフック

### E2E テスト（任意）
- 「テキストを貼り付け → 検査 → 結果表示」のクリティカルパス

## 9. デプロイ戦略

- **ホスティング**: GitHub Pages
- **CI/CD**: GitHub Actions（build → Pages デプロイ）
- **環境変数管理**: なし（シークレットを持たない）
- **プレビュー**: PR では build 検証のみ（インフラストラクチャ規約.md 参照）
