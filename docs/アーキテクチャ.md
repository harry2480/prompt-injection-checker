# プロンプトインジェクション検査サイト アーキテクチャ設計規約

pnpm workspace + Next.js 15 App Router（**静的エクスポート**）における DDD ベースの設計規約。
`apps/webapp/src/backend/` 配下に適用する。

本プロダクトは **GitHub Pages 上の静的サイト**であり、サーバー・DB を持たない。検知処理はすべて**ブラウザ内で動作する純粋な TypeScript ロジック**として実装する。そのため DDD 4層のうち **domain / application を中心に据え、infrastructure の DB・Repository は使用しない**（詳細は「本プロダクトでの適用範囲」を参照）。

---

## ディレクトリ構成

```text
apps/webapp/src/backend/
├── domain/
│   ├── models/          # ドメインモデル（検出結果・リスクスコア等）
│   ├── services/        # 検知エンジン（ルール適用・スコアリング = 純粋関数/クラス）
│   ├── rules/           # 検知ルール定義（データ）: 日本語/英語/言語非依存
│   └── gateways/        # Gateway interface（ファイル読込・URL取得）
├── application/
│   └── usecases/        # 検査オーケストレーション（入力 → 検知 → 結果）
├── infrastructure/
│   └── adapters/        # Gateway 実装（ブラウザ API: FileReader / fetch）+ Stub
└── presentation/
    └── composition/     # Composition Root（DI 組み立て）
```

> DB 接続 (`infrastructure/db/`)・Repository・`presentation/loaders`・`presentation/actions` は**本プロダクトでは不使用**（サーバーが存在しないため）。UI は `apps/webapp/src/frontend/` 側のクライアントコンポーネントから composition 経由で UseCase を利用する。

---

## DDD 4 層構造

| 層 | ディレクトリ | 責務 |
|---|---|---|
| presentation | `presentation/composition/` | UseCase と Gateway 実装の DI 組み立て。フロントエンドへの唯一の公開点 |
| application | `application/usecases/` | 検査オーケストレーション（入力取得 → 検知エンジン呼び出し → スコアリング → 結果整形） |
| domain | `domain/models/` `services/` `rules/` `gateways/` | ビジネスルール（検知ロジック・ルール定義）。外部依存なし |
| infrastructure | `infrastructure/adapters/` | Gateway 実装。ブラウザ API（FileReader・fetch）への接続。Stub を併設 |

---

## 依存方向（厳守）

`presentation → application → domain ← infrastructure`

- **domain は最内層。** 他層への依存禁止。ブラウザ API・DOM にも依存しない純粋ロジック
- **application は domain にのみ依存。** infrastructure への直接依存禁止（Gateway interface 経由）
- **infrastructure は domain/gateways に依存。** interface を implements する
- **presentation/composition は全層を参照可。** UseCase に infrastructure 実装（または Stub）を注入し、エクスポートする唯一の場所
- **フロントエンド** (`frontend/`) **は backend/presentation/composition にのみ依存**。domain・infrastructure を直接 import しない

---

## 本プロダクトでの適用範囲

静的サイト・クライアント完結という制約に合わせ、テンプレート標準の DDD から以下を調整する。

| 要素 | 本プロダクトでの扱い |
|---|---|
| domain（models/services/rules） | **中核。** 検知ロジックとルール定義をここに集約 |
| application（usecases） | 検査フローのオーケストレーション。入力ソースを問わず検知を実行 |
| infrastructure/adapters | ファイル読込・URL取得のみ（ブラウザ API のラッパー）。Stub を用意 |
| infrastructure/db, repositories | **不使用**（DB を持たない） |
| presentation/composition | DI 組み立て。フロントエンドの hook から利用 |
| presentation/loaders, actions | **不使用**（サーバー処理・Server Actions が存在しない） |

検知処理はブラウザ上で同期的に実行されるため、UseCase は非同期を前提にしつつ（ファイル読込・URL取得のため）、検知エンジン自体は同期的な純粋関数として保つ。

## ドメインモデル設計

**Rich Domain Model を徹底する。Anemic Domain Model 禁止。**

- 検出結果（`DetectionResult`）・リスクスコア（`RiskScore`）等の生成・検証・変換はモデル自身のファクトリメソッド / インスタンスメソッドで行う
- 不変条件（スコアの範囲、カテゴリの妥当性等）はファクトリメソッド / コンストラクタで強制する
- domain service に置くのは「複数モデル・複数ルールの協調」のみ。単一モデルで完結するロジックをサービスに書かない

### 検知ルールの表現

- ルールは `domain/rules/` に**データ（配列・定数）として定義**し、コード（検知エンジン）から分離する
- 各ルールは `{ id, category, language: 'ja' | 'en' | 'any', weight, description, matcher }` 等の構造を持つ
- 検知エンジンはルール集合と入力を受け取り、検出結果を返す**純粋関数**として実装する

---

## サービス実装規約

**全サービス（domain service, UseCase）はクラスベース + コンストラクタ DI。関数エクスポートによるサービス実装は禁止。**

- コンストラクタの `private readonly` パラメータで Gateway・ルール集合等の依存を受け取る
- ビジネスロジックは `execute()` 等の public メソッドで公開する
- ヘルパーは private メソッドに閉じる

例外: 型定義 (`interface`, `type`)、ルール定義データ、およびユーティリティ型 (`Result<T, E>` 等) は関数 / 定数エクスポート可。

### エラーハンドリング

- Domain 層のエラー（不正な入力等）は `Result<T, E>` 型で返す
- Application / Infrastructure 層（ファイル読込失敗・URL取得失敗等）は throw する

---

## Gateway パターン

| 種類 | interface 配置 | 実装配置 |
|---|---|---|
| Gateway（ファイル読込 / URL取得） | `domain/gateways/` | `infrastructure/adapters/`（本番 + Stub） |

外部 I/O（ブラウザ API）は必ず Gateway interface を定義し、`infrastructure/adapters/` に本番実装と Stub 実装を用意する。Composition で環境（テスト／本番）に応じて切り替える。Repository は DB を持たないため使用しない。
